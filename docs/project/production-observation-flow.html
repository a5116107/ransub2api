12.1.9 产品化体验合同（2026-11-25）

产品定位：一套能自动维护供给的模型服务经营台，而不是检测工具集合。 管理员设定销售与采购边界，程序检查供应、解释能否服务、保护健康会话并维护候选。运营人员日常处理例外，不需要先理解调度器、TTL、规则拥有者或三种倍率字段。以下为产品设计，未整体上线；离线图文版中的操作仅演示，不发探测、不保存生产配置。

二、入口做减法，不把所有功能挤成一张大表

沿用原运维入口，一级业务导航收敛为经营概览、供应线路、销售产品、待处理。它们是同一个工作台的视图，不新建第二份账号或分组。检测、缓存实验、利润查询和高级配置迁入相关详情，原深链及权限保留；不靠新增大量一级菜单来称统一管理。

经营概览：默认看全部产品及异常；选择一个产品后，模型、时间窗和服务档在各视图联动。禁止把“原有2条开启线路”写成“已认证2条优质线路”。生产G2可显示“按现行规则接单 · 尚未接管”；严格资格缺证据时另标“待验证”，不能以售卖中证明验真。

供应线路列表默认只展示名称、服务状态、适用产品、质量/价格/体验/缓存摘要、最近检查、主要阻断原因和一个“查看”入口。不是每列十几个数。Key、固定上游组、模型映射、共享容量、原账号状态保留在详情，容量满与质量失败分开。

线路详情固定五块：①当前影响/建议动作；②可服务哪些产品与模型；③质量和身份；④体验与缓存；⑤成本与检查记录。每项结论显示测量时间、有效性与“覆盖不足/未测”；详细技术字段置于可展开的“依据”。结论以产品×模型×服务档为范围，某模型通过不让整条线路的所有模型变绿。

销售产品卡展示对外名称、固定销售倍率、允许采购范围、模型/服务档、主力与备用现状、受影响下游、管理方式。“合格数量”只来自统一资格；当前只有开关数量时写“调度开启2条，完整资格待核”。并发10+10只显示配置上限，不能承诺20条随时可用请求或20QPS。

四、自动运行：管理员看供给结果，不管理几十个定时器

允许上游组、倍率、模型、Fast支持等改变，程序只能在明确授权的产品来源和采购区间内重新归类，不能涨用户售价或借更贵线路填补。没有合格线路时明确告知暂不可用。已有会话优先健康原Key/上游组；质量或硬约束失效才合法换线，不因轻微排名波动频繁换号；已输出内容不跨上游拼接，已知文件/加密历史归属需兼容。恢复线路先作备用/接新会话，不抢回健康旧会话。

供应关联移出与供应退役区分：普通“移出本产品”可在再次合格后加回；“暂停新请求”是明确人工限制，程序不撤销；限期排除到期只是撤销排除，不直接放行；供应退役才停新增检测，并保留历史、在途和结算。用户操作文案必须说清这四种后果，避免一个“删除”承担四种语义。

五、检测结果要能读懂，但不能只留一个红绿灯

每个状态组件遵循“结论 + 原因 + 影响 + 操作”。文字、图标和颜色共同表达，不用颜色独占信息；列表一句话，详情有完整依据。整体服务状态、证据可信程度和动作执行状态分别保存语义，在UI组合呈现，不做一项数值能抵消其他失败的总分。

六、异常处理：一条问题、一条影响链、一个最短处理入口

优先级先看“全部供给中断/价格越界”，再看“备用不足/检查体系受阻”，再看“缓存或速度趋势”。每条卡显示受影响产品、首发/最近发生、次数、程序已做什么、是否要人处理和当前配置原因；相同判题池故障不对14条计划各报一遍。独立参考故障标“检查系统受阻”，不是“14条上游降智”。确认价格时只改相关价格来源配置；处理归属时复用原只读预览和明确确认，不批量清历史。

例如当前生产可形成三个配置核对项，不是捏造三条现有自动告警：①主力U/C价格依据不一致，查看开启保护影响；②G2同时供业务和判题，选择已核实参考来源；③只有两条开调度线路且独立故障域未明，查看备用来源。未经读取实时容量不写“只剩2个空槽”，未经完整请求分母不报失败率。

七、利润检查的产品旅程

首层文案用“价格保护”和“估算经营结果”，原profit_control名称可作高级技术标识。启用前预演、运行时准入、历史经营分析是三件事；历史盈利不能证明当前可安全接单。保护范围沿现有文本Token路径，不把独立图片/视频等未覆盖端点做成已保护产品。
